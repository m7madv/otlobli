# حماية كود تطبيق Otlobli بعد النشر

## الحد الأمني الصريح

لا يمكن جعل كود يُنفَّذ على هاتف العميل مستحيلاً رياضياً للاستخراج. يستطيع مهاجم يملك الجهاز مراقبة الذاكرة أو اعتراض النص بعد فكّه أو تعديل النظام. الهدف الصحيح هو:

1. إزالة النسخة السهلة والمقروءة من APK/IPA.
2. رفع كلفة التحليل وإبطال النسخ المباشر.
3. منع النسخة المعدّلة أو المنسوخة من الاستفادة من الخدمات الحساسة عبر قرار يصدر من الخادم.

الذكاء الاصطناعي يسرّع تجميل الكود المستخرج، لكنه لا يعيد أسماء الدوال والمتغيرات التي أزالها المصغّر، ولا يستطيع إنشاء إثبات جهاز صحيح أو توقيع App Store/Google Play صحيح من تلقاء نفسه.

## المطبّق في v86.175

- سكربتا `SHEIN_CAPTURE_SCRIPT` و`OTLOBLI_NAV_BOOTSTRAP_SCRIPT` يُجمعان بالكامل ثم يمران عبر Terser في بناء الإنتاج. هذا يصغّر جسم السكربت نفسه ويغيّر أسماء دواله الداخلية؛ تصغير Vite العادي وحده لا يفعل ذلك لأنه يرى السكربت كسلسلة نصية.
- لا تُنشر source maps، ويمنع فاحص الإصدار رجوع بصمات التنفيذ المقروءة إلى `dist`.
- Android Release يفعّل R8 optimization/obfuscation وresource shrinking وzip alignment، ويعطّل `debuggable` و`jniDebuggable`.
- قواعد Capacitor العامة ضُيّقت: تبقى أسماء plugin وطرق `@PluginMethod` التي يحتاجها الجسر، بينما تُصغّر الحقول والدوال الخاصة بدلاً من إبقاء كامل plugin قابلاً للقراءة.
- Android يمنع backup وdevice transfer لمجلد التطبيق، ويمنع cleartext traffic.
- iOS Release يفعّل dead-code stripping وتجريد رموز المنتج وSwift، مع بقاء dSYM منفصلاً لتفسير الأعطال وعدم شحنه داخل التطبيق.
- إصدارات Capacitor وInAppBrowser المرتبطة برقعة تجمّد iPhone مثبتة بأرقام دقيقة، كي لا يستبدلها تثبيت جديد بإصدار غير مرقّع.
- ملف رقعة InAppBrowser يحتوي placeholders فقط. مفتاح relay الحقيقي لا يجوز أن يدخل Git ويُحقن محلياً/في CI عند البناء المؤقت.
- `npm audit --omit=dev` يجب أن يبقى بلا ثغرات معروفة قبل التسليم.

فاحص هذه الشروط هو:

```bash
npm run verify:release-hardening
```

## ما لا تزال النسخة المحلية لا تستطيع ضمانه

- يستطيع مهاجم متقدم اعتراض سكربت SHEIN بعد أن يفكّه التطبيق في الذاكرة وقبل حقنه.
- أي مفتاح relay ثابت داخل التطبيق قابل للاستخراج من Android أو iOS مهما قُسّم أو شُفّر محلياً؛ وجود المفتاح ومفتاح فكّه في العميل يجعل التشفير تمويهاً لا حداً أمنياً.
- عناوين الخوادم، selectors، مفاتيح Supabase العامة، وأسماء طرق الجسر ليست أسراراً. الأمان يجب أن يأتي من RLS والتحقق الخادمي والحدود، لا من إخفائها.
- R8/Terser وتجريد الرموز ترفع كلفة الهندسة العكسية لكنها لا تمنح منعاً مطلقاً.

## طبقة المنع المطلوبة قبل اعتبار خدمات التطبيق محمية من النسخ

1. ينشئ الخادم challenge عشوائياً قصير العمر لكل عملية حساسة.
2. Android يطلب Play Integrity Standard verdict مربوطاً بـ`requestHash`. يتحقق الخادم من الطلب، ومن `PLAY_RECOGNIZED`، وترخيص النسخة، وسلامة الجهاز وفق سياسة تدريجية.
3. iOS ينشئ مفتاح App Attest ويوقّع challenge لكل طلب حساس. الخادم—وليس التطبيق—يتحقق من attestation/assertion والعداد لمنع replay.
4. بعد نجاح الإثبات وحساب المستخدم، يصدر الخادم relay token لمدة 60–120 ثانية، مربوطاً بالمستخدم والتثبيت والنطاق/الرابط والغرض، ويُستخدم مرة واحدة أو بعدد محدود جداً.
5. يرفض Worker المفتاح الثابت نهائياً بعد انتقال النسخ المدعومة، ثم يُدوَّر المفتاح الحالي. لا يُدوَّر قبل وجود مسار التوكن وإصدار تطبيق متوافق كي لا ينقطع SHEIN عن المستخدمين الحاليين.
6. يبدأ التطبيق بجمع verdicts بلا منع، ثم يُفعّل enforcement تدريجياً مع مسار استعادة واضح للأجهزة السليمة التي تفشل مؤقتاً.

وفق توجيه Apple، لا يجوز الاعتماد على منطق التطبيق ليتحقق من نفسه؛ التحقق النهائي مسؤولية الخادم. ووفق توجيه Google، تكون قيمة Play Integrity الأعلى عندما يتحقق backend من التطابق والتوقيع ويطبّق استجابة متدرجة بدلاً من الاعتماد على إشارة واحدة.

مراجع المنصات الرسمية:

- Android R8: <https://developer.android.com/topic/performance/app-optimization/enable-app-optimization>
- Play Integrity: <https://developer.android.com/google/play/integrity/overview>
- Apple App Attest: <https://developer.apple.com/documentation/DeviceCheck/establishing-your-app-s-integrity>
- Xcode Release stripping: <https://developer.apple.com/documentation/xcode/build-settings-reference>

## قبول الإصدار

- `npm run build` و`npm run verify:release-hardening -- --dist` ينجحان.
- `npm run verify:shein-freeze-guard` و`npm run verify:performance-budget` ينجحان بلا رفع الحدود.
- Android `minifyReleaseWithR8` ينجح وتظهر الدوال/الحقول الخاصة بأسماء مصغرة في `mapping.txt`؛ ملف mapping يبقى خاصاً ولا يدخل APK أو مجلد التسليم العام.
- يُفك APK/IPA تجريبياً للتأكد من غياب source maps وبصمات سكربت SHEIN المقروءة ومفاتيح التوقيع.
- بعد تفعيل attestation: نسخة متجر أصلية تنجح، نسخة معدلة أو معاد توقيعها تُرفض من الخادم، وإعادة استخدام token تُرفض.
- قبول iPhone الحقيقي لتجمّد SHEIN يبقى خمس دورات خلفية/عودة واختبار force-quit/cold-launch مستقل. لا يعوّض البناء أو المحاكي هذا القبول.
